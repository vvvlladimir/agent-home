# Decisions

Newest first within each section. "Provisional" = based on published numbers, not on the owner's

## Architecture

| # | Decision | Why |
|---|---|---|
| D1 | The add-on (Pi 5) talks to a standalone `llama-server` on the Jetson over HTTP. | The add-on cannot run on the Jetson; HA must survive the Jetson being off. |
| D2 | Backend: Python + FastAPI + uvicorn, one process, SQLite (WAL) in `/data`. | Small, async, easy to debug; no extra services on a Pi. |
| D3 | **Python 3.14 at runtime**, 3.12-compatible syntax. | The only current HA Python base image is `base-python:3.14-alpine3.24`; a 3.12 image no longer exists (RESEARCH §1). CI tests 3.13 and 3.14. |
| D4 | (replaced by D25) GUI: **no-build static SPA** with vendored Alpine.js, JSON API, SSE for the live feed. | No Node toolchain in the image, works offline, every URL relative for ingress. The API contract decouples GUI work from backend work. Server-rendered templates would tie each page to its route handler. |
| D5 | i18n: the English text is the key (`t('Kill switch')`); `static/i18n/<lang>.json` maps it. | Complete scaffolding without a string catalogue to maintain; de/ru are one JSON file each. |
| D6 | The Supervisor builds the image locally from the Dockerfile (no `image:` key). | Simplest install for a prototype; wheels only, so the build on a Pi is quick. Prebuilt GHCR images can come with v0.1.0. |
| D7 | Start script uses `#!/usr/bin/with-contenv sh`, no bashio; options are read from `/data/options.json` by the app. | s6 does not pass the environment to `CMD` (verified); the same config code runs in tests. |
| D8 | CI builds with `docker/build-push-action` on native amd64 and arm64 runners. | `home-assistant/builder` is deprecated; a native arm64 runner is the closest thing to the Pi's CPU without hardware. |
| D9 | Orchestrator: official `anthropic` SDK, manual tool loop, default model `claude-opus-5-5`, configurable. | We need policy, budget and trace hooks around every step. Model choice and cost are the owner's call (RESEARCH §6). |
| D10 | Model swapping on the Jetson goes through our small metrics/control endpoint (restart the systemd unit with another profile), not llama-server router mode. | One resident model is the rule on 8 GB; a restart is explicit, visible ("warming") and works on any llama.cpp build. |
| D11 | Default provider: local Qwen on the Jetson once M2 benchmarks pass; cloud is the fallback with `claude-haiku-5-5`. Until then, `claude-haiku-5-5`. Supersedes the `claude-opus-5-5` default in D9. | Owner's answer to Q6 (2026-11-13): Haiku is enough, local first. |
| D12 | The add-on's LLM manager owns the single llama-server slot: priority queue (interactive > agent > background), coalescing by key, stale drop, bounded wait while the model loads, retry only for 5xx / transport / unparsable. | `-np 1` on 8 GB: requests must queue in the add-on, where priorities and staleness are known, not on the Jetson. A timeout is not retried: the slot is busy. |
| D13 | The GUI benchmark and `jetson/bench/bench.py` share `app/core/benchkit.py` and `toolcall_eval.yaml`. Hardware reports come from the Jetson; the GUI run is a quick check of the live setup. | One scoring logic; the GUI cannot restart llama-server between profiles for a cold-load measurement. |
| D14 | Orchestrator providers: `auto` = local first, Claude when the local model fails or is down; `local`; `anthropic`. Cloud spend is stored per day (`spend` table); the worst case of a call (prompt estimate + `max_tokens`, plus a fallback model) is reserved before it and settled after it, so concurrent or failed calls cannot overspend; no SDK retries; a fallback answer is priced at both models; unknown models are priced like the most expensive one. Default model `claude-haiku-5-5`, effort `medium`, strict tools, no forced `tool_choice`; refusal fallbacks only on models that have them. | Owner Q6 + D11; the budget must hold even when a call fails half-way. |
| D15 | The orchestrator only drafts: its single output is a proposal through the lifecycle, traced as a run of agent `orchestrator`. Room agents reach it through `propose_automation` (once per run, never on replays, at most 3 per agent and day). | No second path to HA; the owner sees what the model was asked and what it answered. |
| D16 | Second cloud: OpenAI through the **Responses API** (the GPT-6 models take tools only there), official `openai` SDK, default `gpt-6.1-sol` (mid tier, $2 / $10 like `claude-sonnet-5-5`; `gpt-6-luna` is the cheap one). `store: false`, encrypted reasoning items passed back unchanged, strict tools, no SDK retries; same redaction and the same daily budget as Claude. `auto` = local → Claude → OpenAI, skipping clouds without a key. | Owner request 2026-11-13; model ids and prices from developers.openai.com/api/docs/models (checked 2026-11-13). |
| D17 | The orchestrator gets a first look of 60 entities (request matches first, then up to half room sensors, then devices) plus a `find_entities` search tool; a `decline` before any search is sent back once ("search first"). Read-only sensors are T3 by policy but are not ranked down: triggers need them. | Owner, 2026-11-13: two drafts declined "no desk sensor" while the radar zone sensors existed; all `binary_sensor`s had been sorted behind 80 devices. |
| D18 | Migration: the importer keeps read-only copies of the owner's HA automations (config GET per id), UI scripts and Node-RED exports from `/share/agent_house/nodered/*.json`. A Node-RED export becomes one original per top-level group of a tab; subflow instances are expanded with their `env`; only `server-state-changed`, `ha-time`, `inject`/`cronplus`, `mqtt in`, `server-events`, `api-current-state` and `api-call-service` nodes are read, `function`/`switch`/`change` nodes are counted as "logic not read". A replacement is a normal proposal (`replaces_original`). Parity replays the triggers of both sides against the same history and pairs firings within 60 s; conditions are not evaluated on either side. | The owner's flows are mostly logic in function nodes: a faithful translation is not possible, an honest summary plus a draft the owner reviews is. Replaying both sides the same way compares like with like without needing HA's logbook. |
| D19 | Chat: one turn = one traced run (`wake_source: chat`), answered when the run ends. A room agent answers through its normal runtime (same tools, tiers and shadow mode); the orchestrator has `find_entities` and `submit_automation` only, so it reads and drafts but cannot actuate. Sessions keep the last 8 exchanges in the `kv` table and replay them into the prompt. Config export is agents + policy + GUI settings as YAML (no add-on options, so no secrets); import validates the whole file before writing anything, keeps agents the file does not name, and stores every imported agent in `shadow`. | No second path to HA for chat; a file must not be able to enable actuation ("the owner enables it per agent"). |
| D20 | Habit finder: a deterministic scan of HA's logbook (not the history: only the logbook says what caused a change) over `habit_days` (14) days. A change is *manual* when its context has a user that is not ours, or no context at all (physical switch). A manual `entity → state` of a light/switch/fan/cover/media player/climate/humidifier/input_boolean is a habit when it follows a sensor change (binary_sensor in the same area; person, sun, house mode anywhere) within 3 min on ≥ `habit_min_repeats` (5) days, with precision ≥ 0.3 and recall ≥ 0.5; or when it happens in the same 40-min window of the day on ≥ 5 days and on at least half the days scanned. Entities one of our deployed automations already acts on are skipped. Each candidate is a stored *finding* (keyed by entity, state and trigger, so it is never drafted twice); the daily review (or the owner, from Proposals) hands it to the orchestrator, which drafts a normal proposal; the counts are appended to the rationale as `Evidence:` and the trigger replay runs over the same days. | A model reading raw history is expensive and invents patterns; counting is cheap, repeatable and explains itself. Thresholds are a first guess to tune on the owner's house. |
| D21 | Orchestrator provider per task: `routine` work (the daily review's summary) runs on the local model only, never in the cloud; `draft`, `habit`, `undo` and `conflict` drafts follow `orchestrator_provider`, and with `auto` the cloud is the *expert*: a local attempt that ends without a passing draft (no submission, or a proposal still blocked) is retried once by the cloud alone (the low-confidence case), and the blocked local proposal is rejected in favour of the expert's. No expert without `auto` or without a key. (`core/orchestrator.py` `providers`, `can_ask_expert`) | The Jetson is free and private and good enough for summaries; the cloud is paid per call and only worth it where the small model demonstrably failed. One retry bounds the cost. |
| D22 | Agent council (`core/council.py`): every entity has exactly one owner (room agent of its area, ties to the agent that lists it, else the lowest id; everything without an area or agent to the orchestrator). A shared *board* of short facts with an expiry replaces agent-to-agent chat: nothing on it wakes anyone, at most 8 facts per prompt. The orchestrator owns `input_select.agent_house_mode`; with `auto_house_mode` a deterministic rule picks home / away / night (guests / work are the owner's). Tasks go down (mode change → task per room, the answer is a board report); questions and escalations go up: `ask_agent` and a `report(severity=escalate)` naming another owner's entity are forwarded by the orchestrator as a task to that owner (6 per agent per hour, shared; depth 1: never from a task, chat or poke run); everything else waits for the daily review. The orchestrator's wake rules are fixed (mode change, person change with auto mode, daily review, escalation) and listed with their last firing. A settled conflict between two of our automations is one proposal that changes one and *supersedes* the other (switched off on approval); the review drafts at most one proposal per entity and none beside an open proposal on it (conflict > undo > habit). | Bounded, deterministic coordination: no model decides who talks to whom, no loops, the token cost per wake is capped, and the instant reactions between rooms run in HA via the mode helper. |
| D23 | Room agents run on `qwen35-4b-balanced` (Qwen3.5-4B Q4_K_M, ctx 8192, thinking off); `llm_presence_penalty: 0` is optional (27/36 vs 26/36 tool calls, within noise). `qwen35-2b-fast` stays the fallback only for latency, Gemma 4 E2B is dropped. The orchestrator uses the same resident model for `routine` work and the cloud as the expert (D21). | Owner benchmark 2026-11-13 (`owner-reports/bench/`): 4B 72–75 % tool-call accuracy, warm wake 6.0–6.8 s (target ≤ 8 s); 2B 56 % at 2.4 s; Gemma 4 E2B 69 % at 19.4 s. No profile reaches the 95 % accuracy target, so Shadow Mode, deny-by-default tiers and "escalate instead of guess" stay the safety net, and the room agents go live one by one (RUNBOOK). |
| D24 | GUI layout: a top bar (mode, connection, Stop all) and six tabs (Overview, Activity, Rooms, Automations, Chat, Settings); the old pages are sub-pages, old hashes still work. Overview = decisions waiting (T2 approvals, drafts, findings) + rooms + today's agent activity, marked done / would have (dashed) / blocked. Actions read as "entity: service value"; ids, reasons and help text sit in tooltips or info buttons. Stop all is instant, resume asks. Successes are toasts, errors stay next to their form. | Owner picked mockup A with B's header (2026-11-13); the old 10-item nav and help paragraphs buried the approvals. |
| D25 | GUI in **Vue 3 + TypeScript + Vite** (replaces D4's Alpine): source in `agent_house/frontend/`, `make gui` builds it into `app/web/static/`, and that build is committed, so the image (built on the Pi by Supervisor) needs no Node; CI rebuilds and fails on any difference. Kept light: `vue` is the only runtime dependency (no UI kit, router or store library), hash routing, one shared reactive store, every page but Overview loaded on first open, about 45 kB gzip on first load. API types are generated from `contracts/openapi.yaml` (`npm run gen:api`). Vite `base: './'` plus a rewrite of `index.html` keeps every URL relative for ingress. | Owner wanted reusable components (2026-11-13). Vue is what comparable add-ons use (Music Assistant) and its templates are closest to the Alpine ones. |
| D26 | The simulator gets a control panel on `:8090` (sim-only, never in the add-on). Model backends switch behind fixed local gateways (`:8080`, `:8081`, `:8082`, `:9100`), so the add-on runs unchanged with its simulator settings. Real keys stay in `.data/sim/secrets.json` and are used only by the gateways. Room agents can run on the real Jetson by IP, an OpenAI-compatible host of the same Qwen3.5-4B, OpenAI or Claude, paced to the Jetson's measured speed and context. Generated houses model Zigbee2MQTT and a router (the owner's mess) and are deterministic per seed. | Owner request 2026-11-14: a simulation as close to the real home as possible, with the Jetson reachable by IP or replaced by an API, and no local model on the Mac. With the gateways, nothing in `agent_house/` had to change, and tests stay hermetic: the "real" providers in tests are the fakes. |
| D27 | The orchestrator becomes the **house manager** between reviews (`core/manager.py`, `manager_enabled`, default off). A deterministic prefilter (nobody home or night with lights/media on, failed or escalated room runs, weak automations) runs every `manager_sweep_min`; the model is called only if it finds something, for escalations nobody owns, or on `POST /api/manager/wake`; at most `manager_max_wakes_per_hour`, never with the kill switch. Tools: `call_service` on entities no room agent owns (switchable domains) through the actuator as agent `orchestrator`, shadow unless `orchestrator_mode: live`; `assign_task`; `propose_automation` (new, or a new version of one of ours by `ha_id`, always a draft for the owner); `report`. | Owner request 2026-11-14: a real "manager of the house", not only a daily digest. Prefilter first keeps cloud cost and the no-LLM-unless-needed rule; scope through ownership keeps it out of the rooms' entities; proposals instead of auto-apply keep "drafts until approved". |
| D28 | **Accuracy metrics** without a model (`core/metrics.py`, `GET /api/metrics`): from logbook causes, each change of ours is kept / undone (within 10 min) / unobserved (nobody home, counts neither way) / missed (owner did by hand what it sets). Precision, coverage, F1 per automation, precision per room agent, each with a 95 % Wilson interval and `null` below 5 outcomes; house score = F1 of the micro-averaged rates, plus `score_low` from the lower bounds and `house_share`. Weak = point estimate under 0.6. Daily snapshot in the review. | Owner asked for one number for the whole program that is scientifically sound. Overrides as implicit negatives are the standard signal in adaptive homes; Wilson is correct at small n; unobserved actions would otherwise inflate precision; pooling weighs busy automations properly. |
| D29 | **AI testers on the polygon** (`sim/qa/`): one `sim.polygon serve` and one headless `claude -p` (Haiku) per persona with explicit traits, black box over the owner API and the panel, one finding format; a Qwen3.5-4B coordinator only answers yes/no per candidate duplicate pair (grouping is code); a fresh tester replays each candidate on a fresh polygon and only reproduced items are `confirmed`. Models: orchestrator `gpt-6.1-terra`, room agents Qwen3.5-4B via API for bug hunts (the Jetson for one final run). Testers approve, reject and edit proposals like the owner. | Owner request 2026-11-14. Published multi-agent testing works but produces false positives and over-cooperative users; explicit personas, reproduction and verification address both. The Jetson's single slot would turn parallel testers into timeouts. Details: `docs/POLYGON.md`. |
| D30 | **Claude-only polygon**: a `claude` backend in the sim gateways (`sim/claude_bridge.py`) answers both the room agents' llama-server API and the orchestrator's Messages API with one headless `claude -p` turn per call (no tools, settings, MCP or session; `--json-schema` for `{text, tool_calls}`; model and effort per role). The loop is driven by one lead Claude Code session (skill `/polygon-claude`): `sim.qa up` starts detached polygons and writes briefs, the testers (`qa-tester` haiku, `qa-attacker` sonnet) and verifiers (`qa-verifier` sonnet) are its subagents, the lead judges duplicate pairs itself (`sim.qa pairs` → `coordinate --same`). The add-on's own models cannot be subagents (it calls them over HTTP and waits), so they stay `claude -p`, falling back to the fakes when `claude -p` does not work. `make qa-claude` keeps a headless variant without a lead. Defaults: room haiku/low (a weak model stands in for the 4B), orchestrator sonnet/medium, testers haiku/low, `intruder`/`chaos` sonnet/medium, coordinator = the lead, verifier sonnet/medium. Slow-model limits in that mode: agent `timeout_s` 300, `llm_timeout_s` 300, `llm_stale_after_s` 900. | The owner wants to find the main bugs fast without keys or hardware. Tool calls are emulated through structured output, not native function calling, and Haiku is stronger than Qwen3.5-4B: this finds add-on bugs, it does not measure the Jetson model; D29's Jetson/API runs stay the behaviour check. Smoke run 2026-11-14: `arrive_home` green, 3–8 s per model call. |

## Safety

| # | Decision | Why |
|---|---|---|
| S1 | Unknown domains are T3. Sensor-like domains are T3 too and shown as "read-only". | Deny by default; nothing to actuate there anyway. |
| S2 | A T3 domain can only be lifted by `t3_whitelist` (exact entity ids), and only to T2. | "Never unless the owner explicitly whitelists", and even then a human approves each action. |
| S3 | Agent tier overrides can only tighten. | A prompt or config mistake in one agent must not widen its rights. |
| S4 | Garage covers match `cover.*garage*` → T3 by default. | Covers are T2, but a garage door is a perimeter. Entities named differently need an explicit `entity_tiers` entry (OWNER_CHECKLIST Q4). |
| S5 | The app rejects every peer except 172.30.32.2; no published port; `/healthz` is the only loopback exception. | The GUI can switch modes; it must only be reachable through HA's authenticated ingress. |
| S6 | The M1 HA client is read-only. Service calls and automation writes arrive with the policy engine (M3) and lifecycle (M4), each as the single code path for its kind. | Nothing can actuate by accident before the safety layer exists. |
| S7 | Kill switch also blocks deploys. Already deployed automations keep running in HA. | "Reflexes stay deterministic"; panic-disabling them is a separate, explicit action (M4). |
| S9 | `scene` and `input_boolean` are T2 by default (were T1). | Both act indirectly: a scene can set any entity, a helper can trigger the owner's automations, so their own tier says nothing about what they touch (M3 review). The owner can lower them in `policy.yaml`. |
| S10 | An agent's automatic scope drops device noise (`update`, `device_tracker`, battery/signal/voltage/connectivity sensors, `_linkquality`/`_rssi`/`_last_seen`/… ids; `button` stays), ranks low tiers first (T0 → T3), then room sensors (motion, temperature, …), then other sensors. The first `max_entities` go into the prompt; the rest (up to 200) stay in the allowlist and are found with `list_entities(search=…)`. | A real room has 100+ entities, mostly bookkeeping; a small model gets lost in a long list, but must still reach everything in its room. Tiers apply unchanged. Ranking by use in the owner's automations is not built (M5 importer reads them). |
| S11 | Prompt order: wake-rule entities, then entities the agent read or used (last 30 days, `entity_usage`), then available actuators by tier, room sensors, other sensors; unavailable entities and indicator LEDs (`*_rgb_light`, `*_status_led`, …) last. A quarter of `max_entities` is kept for room sensors. | Owner run r_1a1d4212c23abec23: 20 slots went to unavailable devices and sensor-box LEDs, no sensor was visible, the agent looped. Usage makes the prompt follow what the agent actually needs. |
| S12 | Repeating a read (`get_state`, `list_entities`, `get_history`, `recall`) is allowed, with a "finish now" note from the second time; a repeated identical action is refused once, then the run escalates. `schedule_wake` once per run; neither it nor `ask_agent` on a wake by another agent or by a schedule. | States change, so re-reading is legitimate; actions and agent-to-agent calls are what looped (09:37 ping-pong in the owner's runs). The step limit still bounds every run. |
| S13 | T3 entities of settings domains (`number`, `select`, `text`, `button`, `time`, `date`, `datetime`) rank after the room's sensors; T3 devices with a real state (lock, alarm, camera) keep their tier rank. The default prompt says occupancy changes alone are not worth a report and to describe only states that were read. | Owner run r_1a1d43953a55cf263: six `number.*_off_delay`/`*_countdown` settings sat ahead of the sensors, the model reported a `warning` because someone walked in and described zone states it had not read (owner-reports/m3/README.md). |
| S14 | Automation lifecycle: every create/edit/approve/rollback re-runs yaml → schema → policy → HA `validate_config`. The policy scan accepts only literal `domain.service` calls allowed by the policy (plus `notify.*`, `persistent_notification.create`) on explicitly named, known entities of that domain; blocks T3, the kill-switch helper, `event:` steps, scripts, `automation.*`/`homeassistant.*`, area/device/floor/label targets, templated targets and webhook triggers; recurses into choose/if/sequence/parallel/repeat. Approving a proposal is the owner's approval for its T2 entities. The kill switch blocks approve, rollback and enable; disable and remove stay possible. A config id that exists in HA but was not deployed by us is never overwritten. | Drafts must be harmless until a human says yes, and a deployed automation runs without per-action approval, so the scan is stricter than the runtime policy. |
| S15 | Cloud redaction: `person.*`, `device_tracker.*`, `zone.*` ids become aliases (restored in the answer); the home's, people's and zones' names, e-mails, URLs, IP/MAC addresses, phone numbers, coordinates and keys/tokens become placeholders. Any other entity id that contains a word of such a name (`light.anna_bedroom`) is aliased too. Other entity ids and their states stay (the model needs them). | "Cloud calls carry redacted summaries only"; deny-leaning patterns, verified by a test that greps the fake Anthropic's requests. |
| S16 | "Disable original" is the one write that touches an owner's automation: `automation.turn_off` / `turn_on` on its entity, only from the Migration page on the owner's click (`HAClient.set_original_enabled`, single caller `core/migration.py`). It refuses `agent_house_*` (those go through the lifecycle), never edits or deletes, and is not reachable by any agent or by the orchestrator. The kill switch blocks disabling; enabling again stays possible. Scripts and Node-RED flows cannot be switched from here. An original we switched off is kept in the list even if a re-import no longer sees it. | "Never edit or delete the owner's own automations"; switching off is reversible and visible in HA, and the undo must work in every state. |
| S17 | Council safety: ownership is policy step 2b (`policy.decide`: an agent may only actuate entities it owns, pinned or not) and a lifecycle check (a room agent's draft may only act on its own entities; owner and orchestrator drafts on any). The orchestrator actuates nothing but the mode helper, through the actuator like any agent, in shadow unless `orchestrator_mode: live`. *Supersedes* names only deployed `agent_house_` automations (never the owner's automations or scripts, never the proposal's own id; `guard_ours`), only on owner or orchestrator drafts; approval disables them through `set_enabled(False)` before writing, re-enables them if the write fails, and is refused under the kill switch; the owner turns them back on from the Deployed page. | One owner per entity and one automation of ours per entity are what keep two agents or two automations from fighting; the owner's own automations stay the owner's. |
| S8 | Diagnostics and settings output mask `ha_token`, `anthropic_api_key`, `jetson_token`; a test greps the bundle for the raw values. | The bundle is meant to be committed to the repo. |

| Profile | Model | Settings | Status |
|---|---|---|---|

| `qwen35-9b-experimental` | Qwen3.5-9B Q4 | only resident model; mainline `q8_0` KV first, TurboQuant fork only as an opt-in experiment | experiment |

- The 4B is the only candidate with a third-party Orin Nano measurement (~16 tok/s, 3.9 GB peak;
  RESEARCH §5), which leaves the ≥ 1 GB headroom the memory rule asks for. Not measured by us.
- One resident model. A second one only if the benchmark shows ≥ 1 GB free and no swap use.
- Newer families: nothing found that is clearly better for tool calling on 8 GB. Gemma 4 E2B gets a
  profile in M2 so the owner's benchmark can compare it; Qwen3.5-4B stays the default until then.
- Presence penalty 1.5 is the vendor recommendation for chat; whether it hurts JSON tool arguments is
  an open question for the eval (M2 runs the eval at 1.5 and 0).

## Could not be done in the cloud

- Docker build inside the sandbox cannot reach PyPI through the TLS-inspecting proxy; verified instead
  by installing the pre-downloaded wheels into the real base image. CI does the unmodified build.
- A real HA Core runs headless here (2026.2.3 on Python 3.13); CI runs the same tests on the current
  release. The Supervisor, ingress and the `supervisor/core` proxy cannot be run: see OWNER_CHECKLIST.
